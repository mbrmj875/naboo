# خطة المنتج: ربط واتساب ذاتي لصاحب المحل (Self‑Serve)

**التاريخ:** 2026-08-07  
**النوع:** خطة فقط — لا تنفيذ في هذه الوثيقة.  
**الحالة:** مطابقة لنية المنتج — مثبتة كعقد قبل أي تنفيذ جديد.

**الهدف النهائي:** أي صاحب محل يدخل نابو **وحده**، يضغط «ربط واتساب»، يكمل الربط، ثم يصل إلى «جاهز» — **بدون دعم فني، بدون Dualhook UI، بدون إنشاء قوالب، بدون فهم WABA**.

---

## 0) عقد غير قابل للتفاوض (قبل أي تنفيذ في Cursor)

### 0.1 القالب — الصياغة الصحيحة الوحيدة

> **صاحب المحل لا ينشئ قالباً ولا يرفعه ولا يعرف أصلاً بوجوده.**  
> نابو يضع **تعريف القالب مرة واحدة** في الكود، والنظام يتولى التعامل معه تلقائياً لكل WABA جديد.

| خطأ شائع | الصحيح |
|----------|--------|
| «قالب عالمي واحد تستخدمه كل الـ WABA» | **غير موجود** كرسالة قابلة للإرسال عبر Cloud API |
| تعريف واحد في Naboo + نشر نسخة لكل WABA | **هذا هو المطلوب** |

```
Naboo
  │
  └── DefaultTemplateRegistry
          │
          └── oil_card_lines_ar   ← يُكتب مرة واحدة (مطوّر نابو فقط)
                    │
        ┌───────────┼───────────┬───────────┐
        ▼           ▼           ▼           ▼
   WABA محل 1  WABA محل 2  WABA محل 3  …  WABA محل 100
   (نسخة)       (نسخة)       (نسخة)         (نسخة)
```

عند 100 محل: **لا** يصنع أي محل قالباً. النظام ينشر 100 نسخة من نفس التعريف.

### 0.2 حدود الطبقات (ممنوع كسرها)

| الطبقة | يجوز لها | ممنوع عليها |
|--------|----------|-------------|
| Flutter / شاشات المحل | زر ربط، حالات عربية، طلب إرسال بطاقة | اسم المزود، WABA، Phone Number ID، إنشاء قالب، Dualhook |
| `OilChangeCardNotifier` | `TemplateKey` + متغيرات البطاقة | معرفة Dualhook/YCloud أو استدعاء Graph أو إنشاء قالب |
| `ConnectService` | بدء/إكمال/فصل الربط الذاتي | إنشاء محتوى القوالب أو إرسال رسائل |
| `TemplateLifecycleService` | قراءة Registry + نشر/مزامنة على WABA المستأجر | منطق بطاقة الغيار أو UI |
| `DefaultTemplateRegistry` | التعريف الوحيد لاسم/لغة/مكوّنات القالب | معرفة مستأجر بعينه |
| Transport (Dualhook اليوم) | Onboarding + ensureTemplate + sendTemplate | أن يظهر اسمه فوق طبقة الأعمال |

**قاعدة Cursor قبل أي تنفيذ جديد:**  
لا تجعل `OilChangeCardNotifier` أو Flutter أو أي كود خاص بالمحل يعرف اسم المزود أو WABA أو ينشئ قالباً. كل ذلك يبقى خلف `ConnectService` و`TemplateLifecycleService` و`DefaultTemplateRegistry`.

### 0.3 ملكية المحافظ والحسابات (تصحيح استراتيجي)

> **لا نضع جميع محلات العملاء داخل محفظة «نابو» نفسها.**

| العنصر | المالك الموصى به | الوظيفة |
|--------|------------------|---------|
| محفظة Meta «نابو» | شركة نابو | ملكية **التطبيق**، إعدادات الشريك، الصلاحيات، الاختبارات، التكامل |
| محفظة العميل | صاحب المحل / شركته | الملكية القانونية لأصول واتساب الخاصة بالمحل |
| WABA | المحل | أرقام + قوالب + إعدادات ذلك الكيان |
| `phone_number_id` | المحل داخل WABA | الرقم الذي يرسل ويستقبل |
| تعريف القالب | كود نابو (Registry) | يُنشر **نسخة** داخل WABA كل محل |
| Dualhook | طبقة تهيئة | Embedded Signup / Coexistence / Webhook — الأحداث تصل لخادم نابو |

**النموذج الصحيح:**

```
تطبيق نابو + شريك Dualhook
        │
        ▼  Embedded Signup
محفظة العميل (Meta Business Portfolio)
        │
        ▼
WABA العميل
        │
        ▼
رقم العميل (phone_number_id)
```

**ليس:** `محفظة نابو ← كل أرقام العملاء`.  
نابو = مزود خدمة يحصل على التفويض ويدير عبر API — **وليس المالك النهائي لأصول العملاء**.

| السيناريو | التوصية |
|-----------|---------|
| فروع لنفس الشركة القانونية | محفظة الشركة قد تضم الفروع؛ فصل WABA/رقم حسب التشغيل |
| عملاء SaaS مستقلون (الحالة الأساسية لنابو) | محفظة + WABA لكل عميل عبر Embedded Signup |
| رقم واحد لعدة محلات مستقلة | **غير موصى به** |
| قالب مركزي للإرسال من كل المحلات | **مرفوض** — تعريف في نابو + نسخة API لكل WABA |

**تشخيص الخلط الحالي (قوالب في حساب ورقم في آخر):**  
القوالب على WABA A والرقم على WABA B = سبب التعطل. الاعتماد للإرسال يتطلب الرقم والقالب تحت **نفس** `waba_id`.  
كذلك: WABA أُنشئ عبر «تطبيق المطوّر»/اختبار قد لا يُختار بسهولة من Embedded Signup — لا تبنِ التسجيل الذاتي فوق WABA تجريبي قديم؛ مسار نظيف عبر Embedded Signup لعميل تجريبي حقيقي.

**وضع باقر الحالي:** جدول مطابقة (`business_id` / `waba_id` قوالب / `waba_id` رقم / `phone_number_id`) ثم مسار إنتاج نظيف — بدون حذف عشوائي أو ترحيل عشوائي.

### 0.4 بوابة إلزامية قبل S1 (Dualhook Platform)

قبل تنفيذ مرحلة الربط الذاتي:

1. التحقق أن اشتراك Dualhook الحالي يدعم فعلاً:  
   **Platform / multi-tenant onboarding** + Embedded Signup (+ تخطيط الترقية لإصدارات Meta الحديثة قبل إيقاف v2 إن انطبق) + إدارة WABA المستأجر + إنشاء قوالب عبر API على ذلك الـ WABA.
2. إن **نعم** → الخطة مناسبة كما هي وTransport = Dualhook.  
3. إن **لا** → **لا نعيد تصميم Naboo**. نغيّر فقط طبقة Transport/Onboarding عند الحاجة، ونحافظ على نفس العقود والطبقات أعلاه.

الربط اليدوي لباقر عبر لوحات Dualhook/Meta = **جسر مؤقت**، ليس نموذج المنتج.

4. كل محل معزول (رقمه، حسابه، سجلاته، نسخة قالبه).

## 2) المبادئ المعمارية (ثابتة)

1. **Flutter ↔ Meta/Dualhook: ممنوع** — فقط `whatsapp-gateway` بـ JWT.  
2. **كل محل مستقل:** محفظته + WABA + رقمه (نابو لا تملك أصول العملاء).  
3. **القوالب أصول WABA** — نسخة لكل محل من تعريف Registry واحد.  
4. **ثلاث دورات حياة منفصلة:** اتصال ≠ قوالب ≠ إرسال.  
5. **المزوّد قابل للاستبدال** تحت واجهة Transport دون تغيير Flutter أو Notifier.  
6. **التخزين بالمعرّفات:** `tenant → business_id → waba_id → phone_number_id`.

```
Flutter (زر ربط / حالة / إرسال بطاقة)
    ↓ JWT
whatsapp-gateway
    ├─ ConnectService
    ├─ TemplateLifecycleService  ← يقرأ DefaultTemplateRegistry فقط
    ├─ computeReadyState
    └─ NotificationDispatcher ← OilChangeCardNotifier يعطيه TemplateKey فقط
         ↓
Transport (Dualhook اليوم — قابل للتبديل)
         ↓
Meta (WABA المحل + الرقم + اعتماد نسخة القالب)
```

## 9) خطة دراسة: ثلاث طرق ربط في شاشة واحدة

**الحالة:** واجهة ثلاثية في Flutter + مسار Meta مباشرة مُصحَّح في البوابة (لا يختلط مع Dualhook).  
للتقديم على App Review راجع: [`meta_app_review_submit_ar.md`](./meta_app_review_submit_ar.md).  
**هدف الواجهة:** شاشة «ربط واتساب» أكثر تطوراً — صاحب المحل يختار طريقة واحدة من ثلاث.

### 9.1 ماذا يرى صاحب المحل؟

```
┌─────────────────────────────────────────┐
│           ربط واتساب المحل              │
├─────────────────────────────────────────┤
│  ○ ربط رسمي عبر Meta مباشرة             │  ← الطريقة 1
│  ○ ربط رسمي عبر الشريك (Dualhook)       │  ← الطريقة 2
│  ○ ربط سريع بمسح QR                     │  ← الطريقة 3
│                                         │
│  [متابعة]                               │
└─────────────────────────────────────────┘
```

بعد الاختيار تظهر فقط خطوات تلك الطريقة، ثم نفس الحالات العامة:
**غير متصل → جاري التجهيز → جاهز** (للرسمي) أو **متصل** (لـ QR).

### 9.2 تعريف الطرق الثلاث

| # | الاسم في الخطة | الاسم المقترح في UI | الطبقة التقنية | رسمي؟ |
|---|----------------|---------------------|----------------|-------|
| 1 | **Meta مباشرة** | «ربط رسمي — Meta» | تطبيق Meta لنابو (Tech Provider / Embedded Signup) + تبادل `code` على خادم نابو | نعم Cloud API |
| 2 | **Dualhook** | «ربط رسمي — شريك معتمد» | Dualhook Platform / Connection + Runtime `api.dualhook.com` | نعم Cloud API (عبر شريك) |
| 3 | **QR Code** | «ربط سريع بمسح الرمز» | Evolution أو WAHA — جلسة واتساب ويب | لا (جسر غير رسمي) |

**ملاحظة دراسية مهمة:** الطريقتان 1 و 2 كلاهما Cloud API رسمي. الفرق = **من يدير Onboarding والتوكنات** (نابو مباشرة أمام Meta، أو Dualhook كوسيط). الطريقة 3 مسار استقرار مختلف ومخاطر حظر أعلى.

### 9.3 التدفق لكل طريقة (خلفية فقط)

#### الطريقة 1 — Meta مباشرة
```
زر اختيار «Meta»
  → ConnectService.start(provider=meta_direct | cloud_api_es)
  → رابط/جلسة Embedded Signup من تطبيق Naboo app
  → المحل يكمل Meta
  → خادم نابو يستبدل code → يحفظ business_id / waba_id / phone_number_id / token
  → TemplateLifecycle ينشر القالب على WABA المحل
  → preparing → Approved → جاهز
  → إرسال بطاقة الغيار بقالب
```
**يعتمد على:** اكتمال مراجعة الصلاحيات + Tech Provider للتطبيق الذي أنشأتموه.

#### الطريقة 2 — Dualhook
```
زر اختيار «Dualhook»
  → ConnectService.start(provider=dualhook)
  → جلسة Onboarding Dualhook (Platform)
  → المحل يكمل Meta عبر Dualhook
  → ويب هوك/إكمال يحفظ connection + waba + phone
  → TemplateLifecycle عبر Dualhook Runtime
  → preparing → Approved → جاهز
  → إرسال عبر dualhook_transport
```
**يعتمد على:** اشتراك Dualhook Platform (بوابة S0.5).  
**الوضع الحالي:** باقر مربوط يدوياً على Dualhook — نموذج مؤسس وليس UI ثلاثي بعد.

#### الطريقة 3 — QR Code
```
زر اختيار «QR»
  → setProvider(evolution|waha) + provision
  → عرض QR في التطبيق
  → المحل يمسح من واتساب
  → status=connected → ready فوراً (بدون قالب Meta)
  → إرسال نص/وسائط جلسة (ليس قالب Cloud إلزامياً)
```
**يعتمد على:** سيرفر Evolution/WAHA موجود.  
**في المنتج:** يُعرض كخيار «سريع / تجريبي» مع تنبيه عربي عن الاستقرار ومخاطر الفصل — حسب قرار المنتج لاحقاً.

### 9.4 المعمارية المشتركة (لا تُكسر)

```
Flutter: شاشة اختيار الطريقة + حالة جاهزية
        ↓ JWT فقط
whatsapp-gateway
        ├─ ConnectService      (يفرع حسب الطريقة المختارة)
        ├─ TemplateLifecycle   (للطريقة 1 و 2 فقط)
        ├─ computeReadyState
        └─ Dispatcher
              ↓
     Transport registry:
       meta_direct | dualhook | evolution | waha
```

قواعد ثابتة من §0 تبقى:
- Flutter / Notifier لا يعرفون تفاصيل WABA أو إنشاء قوالب.  
- تعريف القالب مرة في Registry → نسخة لكل WABA في الطريقتين الرسميتين.  
- تبديل Transport لا يعيد تصميم نابو.

### 9.5 ماذا يُخزَّن لكل مستأجر؟

| حقل مقترح | Meta مباشرة | Dualhook | QR |
|-----------|-------------|----------|-----|
| `whatsapp_provider` | `meta_direct` (أو اسم نهائي يتفق عليه) | `dualhook` | `evolution` / `waha` |
| `cloud_waba_id` / `phone_number_id` | نعم | نعم | لا |
| `provider_connection_id` | اختياري | نعم (conn_…) | instance name |
| قوالب `tenant_whatsapp_templates` | نعم | نعم | تُتخطى |
| `ready_state` | preparing/ready حسب القالب | نفس المنطق | connected ⇒ ready |

| ملاءمة «100 محل SaaS» | نعم بعد الموافقة | نعم مع Platform | غير موصى كافتراضي |
| تجربة المستخدم المستهدفة | رسمي | رسمي | احتياطي/سريع |

### 9.7 توصية الخطة (ليست تنفيذاً)

1. **الافتراضي للمنتج النهائي:** طريقة رسمية واحدة ظاهرة بقوة (Dualhook *أو* Meta مباشرة — يُحسم بعد S0.5).  
2. **الثانية الرسمية:** تبقى متاحة إن أردتم مرونة/تدرّج هجرة.  
3. **QR:** خيار ثانوي مع تحذير، أو للمستخدمين القدامى فقط، وليس المسار التسويقي الأساسي.  
4. حتى اكتمال مراجعة Meta App: Dualhook اليدوي/Platform هو الجسر العملي؛ «Meta مباشرة» تُفعَّل في UI بعد جاهزية الصلاحيات.

## 10) جملة الإغلاق

المحل يقول: **«اربط واتساب»** ويختار مساراً واضحاً.  
الرسمي (Meta مباشرة أو Dualhook) = محفظة العميل + WABA + رقم + قالب تلقائي.  
QR = جلسة سريعة منفصلة.  
كل التعقيد يبقى خلف البوابة والـ Registry — والدراسة الحالية تثبّت الثلاث طرق قبل التنفيذ.
