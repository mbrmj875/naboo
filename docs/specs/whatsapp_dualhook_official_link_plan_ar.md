# خطة الربط الرسمي لواتساب نابو عبر Dualhook

**التاريخ:** 2026-08-07 (حدّثت صباحاً بعد اعتماد القوالب)  
**الهدف:** ربط احترافي كامل من الرقم العراقي حتى إرسال بطاقة الغيار من التطبيق.  
**المسار الرسمي الوحيد الآن:** Meta Cloud API عبر **Dualhook**.  
**لا يُستخدم للإنتاج:** YCloud · واتس360 · Evolution/WAHA (إلا حملات/طوارئ صريحة لاحقاً).

---

## 0) جملة واحدة

صاحب المحل في نابو يرى فقط: **ربط → جاري التجهيز → جاهز → إرسال**.  
كل شيء تقني (Meta / Dualhook / قوالب / أسرار) يمر عبر **`whatsapp-gateway`** — ولا يظهر اسم المزود للمستخدم.

## 0‑ب) الواقع الآن (فحص API 2026-08-07)

| الحساب (WABA) | الرقم | القوالب |
|---------------|-------|---------|
| **نابو app** `1207428308207884` | ❌ بلا رقم (حُذف `+1 555…` · اتصال Dualhook ميت) | `oil_change_card_ar` **APPROVED** · `oil_card_lines_ar` **APPROVED** |
| **Naboo** `2504450583349764` | ✅ `+964 788 428 9711` Connected · Phone ID `1203578426161544` | `oil_change_card_ar` **PENDING** فقط · لا يوجد `oil_card_lines_ar` |

**القاعدة الحاسمة:** الرقم والقالب المعتمد يجب أن يكونا على **نفس** الـ WABA.  
اعتماد القوالب على «نابو app» **لا يفعّل** الإرسال من الرقم العراقي حتى تُعتمد نسخة القالب على WABA الرقم.

```
الوضع الحالي (مفصول):

  نابو app ── قوالب Approved ── ✗ رقم
  Naboo    ── رقم Connected  ── ✗ قالب Approved
```


لا Template في الواجهة · لا Dualhook في الواجهة · لا Meta في الواجهة.

### ترتيب العمل هذا الأسبوع (ملخص تنفيذي)

5. **بعدها:** P4 تنظيف · P5 لاحقاً للمحلات الأخرى.

### حقائق تشغيلية مهمة (لا تُنسى)

1. **لا ترسل من الرقم إلى نفسه** — Meta ترفض (`#100 Invalid parameter`).
2. رسائل Cloud API **لا تظهر بالضرورة** في دردشات واتساب على جوال المالك؛ تظهر عند المستلم / صندوق أعمال Meta.
3. سقف أرقام المحفظة الجديدة ≈ **2**؛ بعد توثيق الأعمال أو حد رسائل 2000 → حتى **20**.
4. خطأ YCloud «وصلت الحد الأقصى للأرقام» = محاولة ربط الرقم العراقي **مرة ثانية** على منصة قديمة والسقف ممتلئ بأرقام `+1 555…` — **تجاهل YCloud**.
5. شاشة Dualhook اتصال «نابو» الأمريكي التي تعرض خطأ على `1230151863521411` = اتصال قديم؛ **لا تستخدمه للإنتاج**.

## 7) مخاطر وقرارات صريحة

| مخاطرة | القرار |
|--------|--------|
| خلط اتصال Dualhook أمريكي مع عراقي | مصدر حقيقة واحد: العراقي فقط |
| انتظار القالب وإهمال التوثيق | التوثيق الآن — يرفع الحدود لاحقاً |
| إعادة YCloud | مرفوض للإنتاج |
| رقم واحد لكل محل | كافٍ؛ لا تستهلك السقف بتجارب |
| ظهور الرسائل في جوال المالك | غير مطلوب لنجاح Cloud API |

## 8) تعريف «انتهينا» (Definition of Done)

النظام احترافي وجاهز للإنتاج عندما:

1. باقر مربوط Dualhook بالرقم العراقي فقط.  
2. Business Verification مكتمل (أو مسار واضح بلا حظر إرسال).  
3. `oil_card_lines_ar` = **Approved** على WABA الإنتاج.  
4. من تطبيق نابو: حفظ بطاقة → الزبون يستلم قالب البطاقة.  
5. السجلات والويب هوك يحدّثان حالة التسليم.  
6. وثيقة الدعم هذه كافية لربط محل جديد يدوياً حتى يصل Embedded Signup.

## 9) قرار معماري: القوالب لكل WABA (ليس Global قابل للإرسال)

### الحكم (مبني على وثائق Meta + Dualhook)

| السؤال | الجواب |
|--------|--------|
| هل القالب مملوك للـ WABA؟ | **نعم.** Templates = أصول (assets) على مستوى WhatsApp Business Account. |
| هل يوجد Template عالمي واحد يُرسل منه لكل المحلات بأي WABA؟ | **لا** كرسالة قابلة للإرسال عبر Cloud API. |
| إن كان لكل محل WABA مستقل؟ | يجب وجود **نسخة** من القالب (نفس الاسم/اللغة/المكوّنات) داخل **كل** WABA، وتُراجع/تُعتمد لكل نسخة. |
| ماذا عن Template Library عند Meta؟ | مكتبة **نماذج جاهزة**؛ عند الاستخدام ما زلت تنشئ القالب عبر `POST /<WABA_ID>/message_templates` على الـ WABA الهدف — أي نسخة لكل حساب. |
| Dualhook؟ | صريح: القوالب تُنشأ على مستوى الـ WABA وتُرسل من `phone_number_id`؛ المسارات `…/<WABA_ID>/message_templates`. |

**استثناء تصميمي (ليس Global Template):** إذا وضعت أرقام عدة محلات تحت **نفس** WABA المملوك لنابو، فالقوالب تُشارك داخل ذلك الـ WABA فقط. هذا لا يناسب غالباً SaaS حيث كل محل يربط WABA/رقمه عبر Embedded Signup.

### تصميم نابو الصحيح (Single Source of Truth في الكود)

```
DefaultTemplateRegistry (oil_card_lines_ar, …)   ← يكتب المطور مرة واحدة
        │
        ▼
TemplateLifecycleService.ensureDefaultTemplatesForTenant(wabaId)
        │  POST Dualhook/Meta: /{WABA_ID}/message_templates
        ▼
نسخة القالب داخل WABA المستأجر → PENDING → (webhook) APPROVED
        │
        ▼
computeReadyState → «جاهز» → Dispatcher يرسل بالاسم المعتمد
```

- صاحب المحل **لا يرى** ولا ينشئ Template.
- النظام ينشر التعريف تلقائياً عند أول ربط ناجح فيه `cloud_waba_id`.

### أين في دورة الحياة؟

| الطبقة | الدور |
|--------|--------|
| `ConnectService` | بعد نجاح الربط وحفظ `wabaId`/`phoneNumberId` يستدعي `ensureDefaultTemplatesForTenant` فقط — **لا** يعرّف محتوى القالب. |
| `TemplateLifecycleService` | **النقطة الصحيحة** لإنشاء/مزامنة القالب من الـ Registry ونشره على WABA المستأجر. |
| ويب هوك `message_template_status_update` | يحدّث الحالة → الجاهزية بدون تدخل المستخدم. |

هذا مطابق للكود الحالي تقريباً (`completeOfficialConnect` → `ensureDefaultTemplatesForTenant`). المطلوب تشغيلياً: تعريف كامل لـ `oil_card_lines_ar` في الـ Registry + مسار Dualhook `ensureTemplate` يعمل على كل WABA جديد.
